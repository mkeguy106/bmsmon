## 1 · Context you must have before touching anything

**The Pixel 6 is a dedicated telemetry device, not a phone.** MagSafe-mounted to the wheelchair
frame. The user's daily phone is an iPhone. Wi-Fi only — home Wi-Fi at home, **iPhone hotspot** on
the road (this is how OTA telemetry uploads away from home, and why you lose ADB when they leave).

**The screen is safety-critical, not overhead.** The chair's R-net controller gauge is not
calibrated for the LiFePO4 voltage profile — the flat discharge curve reads "full" almost to cutout,
so it lies. This app is the user's **only accurate reading of remaining charge while out**.
Readability is a safety property. Never trade it for battery. I asserted the opposite mid-session
and was corrected; `CLAUDE.md` records the correction.

**Airplane mode ON is the correct steady state** (SIM reads `OUT_OF_SERVICE`; the modem burns
~28 mA hunting a network it can never join — measured 299 mAh over one night). It is currently ON,
restored and verified 2026-08-08 16:07.
**⚠ Enabling airplane mode also switches Bluetooth off, which kills BLE monitoring.** Restore Wi-Fi
and Bluetooth after, and **verify BLE by packs reporting to the server, not by the adapter flag** —
`State: ON` can be true while nothing has reconnected.

### Device protocol — violating these has cost real downtime three times

Serial: `adb-1C091FDF6003V0-RQzUxy._adb-tls-connect._tcp` (pass with `-s` every time)

- **`adb install -r` only. NEVER `adb uninstall dev.joely.bmsmon`** — ~400 MB of irreplaceable field
  telemetry.
- **`install -r` leaves the app stopped.** Always `adb shell am start -n dev.joely.bmsmon/.MainActivity`,
  then confirm with `ps -A | grep bmsmon`. `monkey -c LAUNCHER` reports success but does **not**
  start this app.
- **Never `am force-stop`** — it bypasses `MotionSource.stop()` and leaves Play Services holding a
  stale PendingIntent.
- **`adb shell input swipe X Y X Y <duration>` is NOT a safe long-press.** Near the top of the screen
  the OS reads it as a notification-shade drag; it toggled airplane mode and left the phone at its
  PIN lock screen. Use held `input motionevent DOWN`/`UP` pairs.
- **Re-derive tap coordinates from a fresh `uiautomator dump` for every tap.** A reused coordinate
  hit the monitoring toggle and stopped monitoring for 90 s.
- The app is usually **screen-pinned** (lock mode), which blocks launching any other activity
  (`am start` fails with error 101) and blocks reaching Settings without a 1.5 s long-press.

### Querying production

`/web/*` endpoints are behind Authentik and return **302** from the dev machine — unreachable. Go
via the NAS:

```bash
ssh joely@ddnas02
docker exec bmsmon-db psql -U bmsmon -d bmsmon -At -c "…"
```

**Use 1-minute buckets, never 5.** Five-minute bucket centroids averaged a real 24 mph drive down to
walking pace and produced a confidently wrong conclusion. Three separate wrong conclusions this
session came from reading an aggregate without checking its resolution could represent the thing
being looked for (broadcast-history indices, 5-minute buckets, a ring buffer).

## 3 · OUTSTANDING — waiting on the user

### 3.1 `MOTION_STALE_MS` tuning — a real decision, deliberately not made
The gate **cycles** rather than holding while parked, because Play Services delivers in bursts with
multi-minute gaps and a reading older than 150 s fails open. Measured: one unbroken 5m18s hold, then
cycling. **So the saving is partial, not full.**

Lengthening the window would reduce cycling, but is only safe if AR reliably emits a confident
non-STILL when motion starts — **untested**. There is now good field data to decide from. Not tuned,
because tuning before the field data would have been guessing, and the final fix wave changed the
duty cycle any tuning would rest on.

### 3.2 AR's power cost — unmeasured, with a **live revert condition**
If periodic Activity Recognition costs more than the ~15 mA the pause saves, **this feature is a net
loss and should be reverted.** Never settled. Per-uid attribution will not work (AR runs inside Play
Services) — compare total phone drain across comparable days from `batterystats`.

### 3.3 The `experiment/ar-power-probe` branch and `dev.joely.arprobe`
A throwaway diagnostic module still **installed on the phone** and subscribed. Decide: keep or
remove. `adb uninstall dev.joely.arprobe` is safe (separate package, never touches the telemetry DB).
**Never** uninstall `dev.joely.bmsmon`. Branch is unmerged.

## 5 · OUTSTANDING — known gaps and deferred work

**5.1 The telemetry gap the new columns immediately exposed.** First prod rows read
`STILL / 100 / motion_still=false` with zero discharge — a confident still reading with the gate
open, past the debounce. Consistent with the bursty-delivery limitation, **but the stored fields
cannot distinguish that from "debounce not yet met", because the reading's age is not uploaded.**
Adding the reading timestamp or a derived staleness flag would close it. Do it *between* diagnostic
cycles, not during one.

**5.2 The screen-hold gate has the charging-icon blind spot.** It holds the display (~139 mA)
whenever `EXTRA_PLUGGED` is nonzero — including on a connected-but-dead charger, the worst case.
Needs hysteresis so it cannot flap. Documented in `CLAUDE.md`, deliberately deferred.

**5.3 Parked minors** (none blocking, all reviewed and triaged as ship-as-is):
- `MotionSource.onSubscribeFailed` guards on the `requesting` boolean, not session identity — a
  stop-then-immediate-restart could let an old task's late failure tear down the new session. Fails
  safe.
- Unthrottled resubscribe if AR is permanently unavailable — a register/IPC/unregister loop on a
  device without Play Services AR. Not reachable on this Pixel.
- The settings "Motion sensing active" line reports permission state only, so it reads "active"
  during the multi-minute delivery silences. Deriving it from `MonitorState` would be honest.
- The DB-size row bypasses the ViewModel and re-runs a `COUNT(*)` already done elsewhere.
- `motion_confidence` is the only `smallint` on `samples`; a clamping validator now protects the
  batch insert.

**5.4 Local `bms.db` is ~404 MB and that is fine.** Retention already runs (14-day samples, 7-day /
20 MB raw frames, every 200 inserts) and the SQLite freelist measured **0 pages** — nothing is
reclaimable, `VACUUM` would free nothing, and 212 GB is free. Shortening retention would starve
`RangeLearn`. Do not "fix" this.

## 7 · How I worked, and what went wrong

Every feature went brainstorm → spec → plan → subagent-driven execution with per-task review, then a
whole-branch review. **The final whole-branch review earned its keep every single time** — it caught
defects no per-task review could see, including two that would have shipped a feature that silently
never activated.

**My own recurring failure was stating conclusions an instrument could not support.** Three times I
read an aggregate without checking its resolution and told the user something false with confidence.
Each was caught by measuring the thing directly instead. If you find yourself about to report a
conclusion from a count, a bucket, or a buffer — check first whether it *could* show what you claim.

**Plan defects that reviews caught, not me:** wrong class names (`Prefs`/`Persisted`,
`SampleIn`/`SampleJson`), a permission requested at only one of two call sites, a `PendingIntent`
that throws on Android 14+, a debounce that behaved as N=1, and a task that queried production for
columns that did not exist there. Briefs in this project have been wrong repeatedly — **implementers
should verify against the code and say so**, and several did.
